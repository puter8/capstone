# 에너지 축 구현·검증 결과

2026-10-14. **로컬 구현·검증 완료, BE 인계 준비 완료.** 사용자 결정에 따라 운영 Supabase 마이그레이션은 BE 담당자가 검토·적용하며 Codex가 직접 적용하지 않는다. 테스트 계정은 미확인으로 BE 준비가 필요하다. 운영 활성화 및 실서비스 전체 검증은 그 이후 진행한다. 실제 서버 설정의 존재 및 대상 프로젝트에 대한 행 0개 조회 HTTP 200을 확인했다. 비밀키는 출력하지 않았다. [BE 전달사항](plan/2026-10-14-energy-be-handoff.md)을 준비했으며 팀 채널 발송은 아직 하지 않았다.

## 구현한 흐름

1. 기존·신규 사용자 모두 최초 1회 영어로 평소 목소리 3개 등록. 화면에서 녹음·다시 듣기·재녹음 후 등록한다. 기준값은 최초 유효 3개 억양 폭 중앙값이며 반복 등록 요청은 덮어쓰지 않는다.
2. 기존 브라우저 WAV 변환을 재사용한다. 인증된 발화를 저장할 때 PCM 음성·해시·세션 회차를 작업 정보로 함께 저장한다.
3. 별도 worker가 pYIN을 순차 실행한다. DB lease와 token으로 작업을 회수·완료하며 재시작 후 만료 lease를 회수할 수 있다. 처리 완료·결측·실패 시 작업 원음을 제거하고 측정값·해시·사유만 남긴다.
4. 발화 응답은 pYIN 완료를 기다리지 않는다. 대화 중 Energy는 직전 확정 음성 점수(없으면 중립 초기값 50)를 유지한다. 텍스트 규칙의 Energy를 섞지 않는다.
5. 세션 종료 시 해당 회차의 유효 발화 최소 5개 중앙값에서 개인 기준값을 뺀 Δ로 `clip(50 + 10×Δ, 0,100)`을 계산하고 5점 단위 반올림한다.
6. 미완료 작업·기준 부재·유효 표본 부족이면 에너지를 갱신하지 않고 사유를 반환한다. 종료 스냅샷은 고정되며 늦게 끝난 작업이 이미 공개한 값을 바꾸지 않는다.
7. 종료 응답, 히스토리, 다음 대화 시작값, 프로필 태그가 같은 스냅샷을 사용한다. 프론트는 종료 응답을 받은 뒤에만 캐릭터 누적 상태를 공개한다.

캐릭터 시각 매핑 자체는 변경하지 않았다. ‘연속 두 세션 같은 단계일 때 변경’ 같은 디자인 안정화 규칙은 측정 점수와 분리하여 향후 5축 재매핑 때 다룬다.

## 측정 재현

사용자 WAV 10개 모두 측정되며 첨부 결과와 소수 첫째 자리 수치가 일치했다.

- 옥타브 접힘 휴리스틱 후 클립별 폭: 3.50, 2.16, 1.90, 5.10, 6.90, 4.80, 4.92, 3.76, 4.16, 6.10 반음.
- 중앙값 4.48반음, 표준편차 1.502반음.
- 4,000회 재조합(seed=1): 낮음 5.475%, 중간 87.9%, 높음 6.625%.
- 첫 실행 4.893초, 이후 0.370–1.187초. 로컬 측정값이며 운영 속도 보장이 아니다.
- 정확한 단계 경계는 점수의 5점 반올림을 포함할 때 Δ ±1.75반음이다. 첨부의 ±1.7은 근사 설명이다.

첫 3개 녹음으로 기준을 만들고 다음 5개를 세션으로 집계한 계산 연결 예시에서 Python과 SQL 모두 **기준 2.16, 세션 4.92, Δ +2.76반음, Energy 80점**을 반환했다. 같은 자료로 만든 기능 검증 사례이며 사람 평가 정확도나 독립 시험 결과가 아니다.

## 검증 근거

| 범위 | 결과 | 제한 |
|---|---|---|
| Python 계산·worker·API·기존 TTS/턴 회귀 | 71개 통과 후 종료 응답 검증 강화. 관련 API 14개 재검증 통과(기존 12개+새 2개) | 외부 DB·음성 서비스는 대역 사용. 전체 고유 검사 73개 |
| 실제 PostgreSQL 엔진(PGlite) | 기존 종료 migration과 새 migration 실행, 18개 검사 통과 | 축소한 기존 스키마에서 실행. 운영 스키마 적용은 아님 |
| 실제 녹음 → Python 집계 → PostgreSQL 계산 | 기준·중앙값·Δ·점수 일치 | 실제 사용자 세션 저장 E2E는 아님 |
| 프론트 TypeScript·API 계약·Energy 경계 검사 | 통과 | 배포 검증은 아님 |
| 실제 Chromium 360×800 | 짧은 녹음 거절, 3개 녹음·WAV 변환·재생·등록 상태, 가로 넘침 없음 | 가상 마이크·등록 응답 대역을 사용한 격리 UI 검증 |
| 운영 Supabase 연결 | 대상 프로젝트 확인, 행 0개 조회 HTTP 200 | 사용자 행·음성 작업 쓰기는 수행하지 않음 |

SQL 검증에는 사용자 격리/RLS, 클라이언트 직접 변경·RPC 차단, 반복 완료, pending 종료 고정, 늦은 worker, 재개 회차 불일치 차단, lease 만료 회수, stale token 차단, 5점 ties-to-even 반올림을 포함한다. 다중 인스턴스 부하 시험을 했다는 뜻은 아니다.

## 아직 수행하지 않은 것

- 운영 DB에 `supabase/migrations/20261014040000_voice_energy.sql` 적용.
- 적용된 스키마의 Supabase 타입 재생성 및 실제 프로젝트 호환성 확인.
- 테스트 계정의 실제 마이크 → STT/Gemini/TTS → DB 음성 작업 → worker → 종료 스냅샷 → UI 전체 검증.
- 실제 운영 동시 접속 조건의 응답 지연 측정.
- 여러 사용자·의도적 억양 대비 조건에서 에너지 신호 신뢰도 검증.

`PALLY_VOICE_ENERGY_ENABLED` 기본값은 false다. 위 운영 적용을 완료한 뒤 활성화해야 한다. 신규 프론트는 `/api/energy/baseline`을 조회하므로 해당 API가 있는 백엔드와 함께 배포해야 한다. 코드는 준비됐지만 운영 적용 완료로 보고하지 않는다. 이번 작업에서 환경설정 키·캐릭터 디자인을 변경하거나 배포·커밋하지 않았다.
