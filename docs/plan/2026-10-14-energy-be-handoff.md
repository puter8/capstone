# BE 전달사항 — 에너지 축 구현 및 로컬 검증 완료

2026-10-14 사용자 결정: **운영 DB 마이그레이션은 BE 담당자가 검토·적용한다. Codex는 직접 적용하지 않는다.** 현재 전달용 문서이며 팀 채널에 발송한 상태는 아니다. 테스트 계정은 미확인 상태로 BE에서 준비가 필요하다.

## 전달 메시지

에너지 축 코드와 로컬 검증을 완료했습니다. 사용자별 평소 목소리 3개로 기준을 등록하고, 대화의 유효 발화 5개 이상을 모아 개인 기준 대비 억양 폭 변화로 Energy를 계산합니다. 기존 사용자도 최초 1회 등록합니다. 측정은 응답 경로 밖의 worker에서 처리하며, 점수·캐릭터 상태는 팀 확정 정책대로 세션 종료 후 공개합니다.

운영 DB에는 아직 적용하지 않았습니다. 아래 migration 검토·적용과 테스트 계정 준비를 BE에 요청드립니다. 기능 기본값은 `PALLY_VOICE_ENERGY_ENABLED=false`이며, 운영 E2E와 지연 확인 전에는 전체 사용자에게 활성화하지 않습니다. 캐릭터 디자인 매핑은 이번 변경에 포함하지 않았습니다.

## 전달할 변경

| 구분 | 파일·역할 |
|---|---|
| DB migration | `supabase/migrations/20261014040000_voice_energy.sql` |
| 계산 | `ai/voice_energy.py` |
| 작업 처리 | `backend/lib/voice_energy.py` |
| API 연결 | `backend/main.py`의 기준 등록·발화 저장·종료·히스토리·다음 대화 연결 |
| 의존성 | 루트 및 `backend/requirements.txt`: `librosa==1.0.0` |
| 설정 예시 | `backend/.env.example`: `PALLY_VOICE_ENERGY_ENABLED=false` |
| 프론트 | `EnergyBaselineRegistration.tsx`, 홈 화면, API 계약·클라이언트, 녹음 hook |

현재 작업 트리에 다른 작업의 미커밋 변경도 많습니다. 저장소 전체를 일괄 반영하지 말고 관련 변경을 검토해 분리해 주세요. 이 문서는 특정 커밋이나 배포가 완료됐다는 의미가 아닙니다.

## DB 검토 사항

- 기존 `messages`에 `voice_energy` JSONB와 `voice_energy_epoch` 열 및 pending 작업 인덱스 추가.
- `voice_energy_baselines`: 사용자별 최초 기준값·측정 요약 저장.
- `voice_energy_snapshots`: 세션·재개 회차별 확정 축과 측정 상태 저장.
- 기준 등록, 작업 claim/finish, 종료 집계 RPC 및 회차 검증 trigger 추가. 기준·스냅샷은 일반 클라이언트가 직접 수정하지 못하게 권한을 제한한다.
- `20261005200000_session_feedback_request.sql`의 `complete_conversation_with_feedback`와 기존 세션/메시지 구조에 의존한다. 운영에 이 선행 변경이 적용되어 있는지 확인해야 한다.
- 원음은 작업 입력으로 DB에 잠시 저장하며 정상 완료·결측·실패 시 제거한다. worker가 중단되면 pending/processing 원음이 남을 수 있으므로 작업 재개·lease 회수와 적체 상태를 확인해야 한다.
- 종료 시 아직 처리 중이거나 유효 발화가 부족하면 이전 Energy(최초에는 50)를 유지하고 사유를 저장한다. 늦은 결과로 확정된 세션 점수를 다시 바꾸지 않는다.
- 원본 녹음, 환경설정, 키를 커밋하거나 전달 문서에 붙이지 않는다.

## 로컬 검증 결과

- 실제 사용자 WAV 10개 측정 성공, 첨부 수치 재현.
- Python 고유 검사 73개: 71개 통합 통과 후 종료 응답 검증 강화에 대한 API 14개 재검증 통과(기존 12개+추가 2개).
- 실제 PostgreSQL 엔진(PGlite), 축소 기존 스키마에 선행·신규 migration 실행: 18개 검사 통과. 운영 스키마 자체에 적용한 검증은 아니다.
- 실제 녹음 측정값의 Python/SQL 집계 일치: 기준 2.16반음, 세션 4.92반음, Δ 2.76반음, Energy 80점. 정확도 평가가 아닌 계산 연결 사례다.
- TypeScript·API 계약 검사 통과. Chromium 360px 녹음·재녹음·WAV 변환·등록 화면 확인. 가상 마이크·저장 응답 대역을 사용했으므로 실서비스 E2E와 구분한다.
- 운영 Supabase는 행 0개 조회 HTTP 200만 확인했고, 사용자 데이터 쓰기·migration 적용은 하지 않았다.

검증 상세: [구현·검증 결과](../energy-implementation-validation-2026-10-14.md). 로컬 `data/models/`의 JSON·스크린샷은 git 제외 자료라 코드 전달만으로 공유되지 않는다. 필요하면 원음·키를 제외한 결과 요약을 별도로 전달한다.

## BE 적용·검증 순서

1. 관련 변경 검토, 선행 migration·운영 스키마 확인, 테스트 계정 및 검증 환경 준비. 가능하면 분리된 검증 DB에서 먼저 실행한다.
2. 새 migration을 BE가 적용하고 Supabase 타입을 재생성한다.
3. 의존성을 설치한 신규 백엔드를 기능 비활성 상태로 확인한다. 신규 프론트는 `/api/energy/baseline`을 호출하므로 이 API가 있는 백엔드보다 먼저 배포하지 않는다.
4. 테스트 환경의 백엔드에서만 기능을 활성화해 기준 등록 3개 → 실제 발화 5개 이상 → worker 완료 → 세션 종료 → DB 확정 값과 화면 전달 값 일치를 검증한다. 현재 플래그는 서버 전체에 적용되며 계정별 제한 기능은 없다. 테스트 계정 하나로 확인하려고 운영 서버 전체 플래그를 먼저 켜면 안 된다.
5. 유효 발화 부족, 측정 중 종료, 반복 종료, 대화 재개, lease 만료 복구, 다른 사용자 접근 차단도 확인한다.
6. 실제 응답 지연·CPU·메모리·작업 적체를 확인한 뒤 운영 활성화 여부를 결정한다. 백그라운드 계산도 자원을 쓰므로 ‘속도 영향 없음’을 보장하지 않는다.

문제가 있으면 기능 플래그 비활성화를 우선 검토하고 새 기준·스냅샷 테이블을 즉시 삭제하지 않는다. 비활성 상태는 기존 텍스트 Energy 경로로 돌아가므로 기존 음성 결과의 표시·복원 차이도 확인해야 한다. 공유 DB 변경·데이터 삭제는 별도 검토 없이 실행하지 않는다.

## BE에서 회신받을 내용

- 선행 및 신규 migration 적용 여부와 검증 환경
- 사용할 테스트 계정과 로그인 방법(비밀키·비밀번호의 채팅 공유 불필요)
- 실제 음성→저장→worker→세션 종료→화면 검증 결과
- 응답 지연·작업 적체 확인 결과 및 운영 활성화 판단
