## [AI]

### Rule-based 유지 이유

발화 5개의 **진짜 정답 Curiosity 점수**가 이렇다고 하자:

| 발화 | 정답 |
| --- | --- |
| "I like pizza." | 5 |
| "Why do you think that happened?" | 90 |
| "That's interesting, tell me more!" | 70 |
| "I finished my homework." | 10 |
| "What's the difference between these words?" | 85 |

**Rule-based**: 질문부호, "why/what" 같은 실제 단서를 보고 판단 → 예측값 `[10, 80, 65, 15, 75]` — 가끔 좀 틀리지만 순서(누가 더 궁금해하는지)는 제대로 따라감.

**ML(데이터 부족)**: 확신이 없으니까 "모르겠으면 평균값 근처로 찍는 게 평균 오차를 줄이는 데 유리하다"는 걸 학습해버림 → 예측값 `[45, 55, 52, 48, 58]` — 전부 50 근처로 뭉뚱그림.

여기서 **평균 오차만 계산하면** ML이 의외로 나쁘지 않게 나올 수 있어(극단적으로 크게 틀리는 경우가 없으니까). 근데 **입력을 구분하는 능력**을 보면 완전히 다르지 — rule-based는 5점짜리 문장과 90점짜리 문장을 확실히 다르게 찍는데, ML은 45~58 사이에서만 왔다갔다 해서 **사실상 "이 문장이 궁금해하는 문장인지 아닌지"를 거의 구분 못 하는 거야.** 입력이 뭐든 비슷한 값을 내놓으면, 상관관계(Spearman) 계산하면 거의 0에 가깝게 나와 — 이게 실제로 우리 Curiosity 축에서 나온 숫자(rule 0.79 vs ML 0.04)야.

Pally 입장에서 중요한 건 "평균적으로 덜 틀리는 것"이 아니라 "캐주얼한 말이랑 궁금해하는 말을 실제로 다르게 반응하는 것"이라서, 지금은 rule-based가 이 기준에서 명확히 나은 거야.

### 진행현황

#### 1. 배경 — 문제 정의

5축 ML 분석기 학습 데이터가 **30개뿐**(원래 목표 150~300개). Week5에서 "데이터 부족 → rule-based 유지"로 결정했는데, 이 결정이 지금도 맞는지 데이터를 실제로 늘려서 재검증하기로 함.

#### 2. 데이터셋 문제 — 공개 학술 데이터셋 6개 조사, 전부 실패

| 데이터셋 | 탈락 사유 |
| --- | --- |
| SQUINKY / GYAFC / XFORMAL (Formality) | 뉴스·블로그 글쓰기체, 회화체 아님. GYAFC는 academic use만 허가 |
| Curiosity Dataset (Facebook, EMNLP 2020) | **CC-BY-NC-4.0** — 상업 서비스 지향 Pally엔 이용 불가 |
| Quantifying Intimacy in Language (Pei & Jurgens) | 라이선스(MIT)는 괜찮은데 실제 내용이 r/AskReddit류 정치·성·마약 주제 — Reddit 원문 금지 정책 위반 + 회화체 아님 |
| INTIMA | AI 동반자 관계 **안전성 테스트 벤치마크**(정서적 취약성 표현 모음) — 학습용 아님 |
| "My Boyfriend is AI" (MIT Media Lab) | Reddit 원문 + 도메인(AI 연애 감정) 완전히 무관 |
| Eight-emotion-sentics (MIT) | 텍스트 아니라 생체신호 데이터 |
| EmoBank | 라이선스·출처는 통과(Reddit 아님, 상업 가능)했지만 실제 내용이 소설·블로그 산문이라 회화체 수확률 극히 낮음(25개 중 1~2개) |

**결론**: "Reddit 아니고 안전하고 회화체인 공개 데이터셋"은 구조적으로 존재하지 않음.

#### 3. LLM 보조 라벨링으로 전환

`docs/ai-labeling-guide.md` 기준을 그대로 반영한 프롬프트를 Gemini/GPT/Claude 세 곳에 요청 → Gemini 110개, GPT 99개, Claude 100개 = 309개 확보.

#### 4. 검증 결과

- 자동 검증(스키마·범위·중복·문어체): **3개 소스 전부 오류 0건**, style 11개 카테고리 고르게 분산
- 소스 간 중복 1건 발견·제거
- **수동 발견**: GPT는 style 카테고리와 Curiosity 점수가 거의 기계적으로 붙어있음(`opinion`=항상 0~2 등) — AI 라벨러 편향의 실제 사례

#### 5. 데이터 병합: 30개 → 338개

`data/axis_dataset_week2.jsonl`에 반영(train 254/dev 37/test 47). **아직 git 미커밋** (현재 브랜치 `gsd/phase-ai-reply-length`, 새 브랜치 필요).

#### 6. 재평가 — 30개 vs 338개 (핵심 결과)

|  | 30개 | 338개 |
| --- | --- | --- |
| rule MAE | 16.18 | 16.54 (데이터 늘려도 안 바뀜 — 룰베이스는 학습을 안 하니까) |
| ML MAE | 13.81 | **12.44** |
| hybrid MAE | 13.10 | 13.34 |

**축별 Spearman(구분 능력) — 가장 중요한 변화:**

| 축 | rule | ML(30개) | ML(338개) | hybrid(338개) |
| --- | --- | --- | --- | --- |
| Curiosity | 0.76 | **0.04**(붕괴) | **0.72**(회복) | **0.79**(최고) |
| Formality | 0.63 | 0.26 | **0.71** | **0.76** |
| Intimacy | 0.41 | 0.13 | **0.57** | **0.60** |
| Energy | 0.54 | 0.35 | 0.56 | 0.62 |
| Humor | 0.52 | 0.22 | 0.52 | 0.56 |

**→ hybrid가 5축 전부에서 rule과 동률이거나 앞섬.**

#### 7. 20턴 EMA 시뮬레이션 (실제 대화처럼 누적)

- **30개일 때**: ML이 같은 스타일 구간 안에서도 계속 출렁거림(35~80), 캐주얼(44 평균)이 격식체(53 평균)보다 낮다는 보장도 없었음
- **338개일 때**: "궁금해함" 구간에서 안정적으로 높게 유지(ML 66~76), 캐주얼 구간은 낮은 값(13~17)으로 수렴 — 실사용 가능한 수준으로 개선

#### 8. 실제 데모 3케이스 콘솔 검증

캐릭터를 움직이는 `tone_casual`/`energy_level`/`humor_level` 기준, Persona drift(캐주얼→격식) 케이스에서 rule 52→50→39→36→35, hybrid 52→49→38→34→37로 **거의 동일한 하락 패턴**. 튀는 값 없음.

#### 9. AI 생성 데이터 자체의 한계 (미해결 논점)

- AI가 만든 데이터를 무한히 늘리는 건 해법이 아님: (1) 같은 생성 분포 안에서 밀도만 늘어남(진짜 다양성 아님), (2) 라벨 자체가 AI 판단이라 "AI 라벨과 잘 맞는다"를 확인하는 순환 논리
- 대안(미착수): 팀원 직접 예문 작성, 실사용 데이터 점진적 확보, EmoBank는 검증용으로만 소량 활용

### 전달사항

#### → PM

- **계정 삭제 — 재인증 방식 결정 필요**: 비밀번호 재입력 / OAuth 재동의 / OTP 중. 결정 전까지 기능 **비활성(fail-closed)** 상태로 안전하게 대기. 보존 2년은 이미 코드에 반영.
- **결제 실연동 — 사업자등록번호 + 가맹 계약 + 정산 계좌**가 필요

#### → AI

- **인터페이스 변경 없음, 참고만**: `generate_feedback`의 `(items, failed)` 계약 그대로 씀. 이제 `failed=True`면 백엔드가 `messages.feedback`에 **`null` 저장**(기존 `[]` → null). "생성 실패"와 "교정 없음(`[]`)"을 DB에서 구분하기 위함.
- **feedback backfill 붙일 여지 생김**: 실패분은 `messages.feedback IS NULL`로 조회 가능 → 나중에 재생성 로직 붙일 때 대상 특정 쉬움.
- `reply_shaping` / `analyzers`(get_axis_analyzer)는 계속 호출 중 — 시그니처 유지 부탁.

#### → FE

- **turn 응답에 `feedback_pending`(bool) 추가** (turn 생성 + History 상세 둘 다): `true`=피드백 생성 실패/미완(재시도 안내 가능), `false`+`feedback=[]`=교정 없음. → **W7 배포 후 반영.**
- **동시 중복요청**(같은 `Idempotency-Key`) 이제 503 대신 **`replayed` 정상 결과** 반환 → 재시도 UX 개선.
- **계정 삭제 API**: `POST /api/account/deletion-request`(현재 503 미활성), `GET`으로 상태 조회. 활성화 전까지 UI 비활성 처리.

## 사람 검수 데이터

각 행에서 점수 5개 + reviewer_id + review_status만 채우면 됩니다. review_set, review_id, 발화와 앞뒤 문맥은 수정하지 마세요.

점수 기준:

- Formality: 0 매우 캐주얼, 100 매우 격식적
- Energy: 0 차분함, 100 강한 흥분·강조
- Intimacy: 0 거리감·업무적, 100 개인적·친밀함
- Humor: 0 유머 없음, 100 농담·장난 중심
- Curiosity: 0 질문/탐색 없음, 100 강한 질문·확인·탐색

예시 행의 발화는 말더듬과 right?가 있어 비교적 캐주얼하고, "definitely out"은 약간의 강조가 있으며, 확인 질문이므로 Curiosity는 중간 이상으로 볼 수 있습니다.

**작성예시**

```csv
gold,gold-0001,"Um the flat co completely flat case is definitely out, right?",yeah.,Yeah,35,55,20,0,65,reviewer-01,completed,"Casual task discussion; emphatic confirmation question."
```

Notion 원본에는 `gold-0001`~`gold-0200` 200행의 빈 검수 시트(CSV)가 붙어 있다. 같은 200행은 검수 완료본(평균 점수)으로 저장소에 이미 있으므로 여기에 다시 싣지 않는다.
