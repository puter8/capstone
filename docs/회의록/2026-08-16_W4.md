## [AI] api 수정 사항

### 수신: Backend (BE) — AI 파트 관련 요청 (요약)

- **P0 — 멱등성(idempotency) 완전 구현**
  - 현재: `Idempotency-Key` 헤더 존재만 검사(`require_idempotency_key`)하고 있음.
  - 필요: 요청 fingerprint(오디오 SHA256 + normalized path + form fields) 비교·저장용 `idempotency_keys` 테이블 + 상태(status=processing|completed|failed) 도입. 동작:
    - 동일 key + 동일 fingerprint → 저장된 `response` 재반환
    - 동일 key + 다른 fingerprint → 409 `idempotency_conflict`
    - 동일 key 처리 중 → 409 `idempotency_in_progress` (응답에 `Retry-After`)
  - 이유: 모바일/네트워크 재시도 시 중복 과금·중복 외부 호출 방지.
- **P0 — Turn API에 feedback 통합**
  - `_call_gemini_feedback`(legacy, `/api/feedback` 전용, shape 다름)는 재사용/재구현 불필요. `create_turn` 오케스트레이션 안에서 `ai.generate_feedback.generate_feedback(transcript, reply, session["level"])`를 그대로 호출해줘.
  - 반환값이 `(items: list[dict], failed: bool)` 튜플로 바뀌었어(기존 BE 질문 답변 때 알려준 `list[FeedbackItem]` 단일 반환에서 변경됨 — 실패 신호가 없으면 partial 규칙을 못 지킬 것 같아서 추가함, latency/timeout 10s는 동일).
  - `items`는 `messages.feedback`에 그대로 저장(순서대로 `id` 부여는 BE 몫). `failed=True`면 `status: "partial"` + `warnings: [{"code": "feedback_failed", ...}]`로 응답 — `items`가 `[]`여도 이땐 "교정 없음"이 아니라 "생성 실패"라 구분해줘. `failed=False`이고 `items=[]`이면 정상적인 "교정 없음"이야.
- **P0 — TTS: inline base64 → Storage 업로드 + signed URL**
  - 현재: TTS 응답이 base64를 일부 엔드포인트에서 사용함(README/코드).
  - 필요: TTS 음성은 백엔드가 바이트를 Storage(예: Supabase Storage or GCS)에 업로드하고, 15분 유효한 `audio_url`(signed)와 `audio_expires_at`을 반환. 응답 필드명은 `pally.audio_url`, `audio_expires_at`으로 통일.
  - 이유: 오디오 크기/전송 비용·캐시·CDN·보안상 유리. FE는 signed URL을 재요청하여 갱신 가능.
- **P0 — Quota(사용량) 원자적 예약 처리**
  - 현재: quota 관련 로직 없음.
  - 필요: 요청 수락 시 DB에서 원자적으로 '예약' (RPC `reserve_turns(user_id, date_kst, 1)`), 실패 시 예약 해제(`rollback_reservation`), 성공 최종 처리 후 `finalize_turns`. 동시성 테스트 필요(마지막 1회 동시요청 시 하나만 성공).
  - 이유: 동시 요청 시 초과 사용·중복 차감 방지.
- **P0 — Conversation-level processing lock**
  - 필요: 동일 `conversation_id`에 대해 동시에 처리되는 `processing` turn을 1개로 제한 (DB lock 또는 `conversation_locks` 테이블). 다른 요청은 `409 turn_in_progress`.
  - 이유: turn 순서·일관성 보장, 중복 생성 방지.
- **P0 — 응답 필드 정합성, 에러 코드**
  - 응답 형식(에러 포함)을 API 명세(Section 6) 형식 `{"error": { code, message, request_id, details? }}`으로 일관화(코드에는 AppError 사용 중이라 양호).
  - `create_turn` 결과에 `axes`·`character`·`feedback[]`·`quota`·`warnings` 포함(명세 샘플을 따름).
  - `speech_not_recognized`, `ai_engine_failed`, `stt_failed`, `persistence_failed` 등의 에러 반환 규칙을 문서화해 FE와 공유.
- **P1 — Feedback 실패와 partial 규칙**
  - 피드백 생성 실패는 전체 실패가 아닌 `status: "partial"` + warnings(`feedback_failed`)로 저장/응답.
  - TTS 실패는 `tts_failed` 경고, `pally.audio_url = null`, 응답은 partial로 처리.
  - DB 저장 실패는 즉시 503 `persistence_failed`.
- **P1 — Schema / Pydantic 모델 동기화**
  - `FeedbackItem`(`original`, `corrected`, `explanation_ko`)은 AI가 `ai/contracts.py`에 이미 추가해뒀어. BE는 여기에 `id`만 얹어서 자체 응답 모델(`backend/main.py` 또는 향후 `schemas/`)을 이 shape과 맞춰줘. FE 공유 TS 타입(`types/schemas.ts`) 자동 생성은 권장 사항으로 유지.
- **P1 — STT/turn 길이·크기 규칙 일치**
  - README: `/api/stt`에 60초 언급. Spec: turn 오디오는 최대 **30초·10 MiB**. 정합 필요: BE는 turn용 제한(30s/10MiB), `/api/stt`는 개발용으로 60s 허용할 수 있지만 명시적으로 구분해 문서화 필요.
- **P1 — Storage path 및 ownership**
  - Storage 경로 권장: `{user_id}/{conversation_id}/{turn_id}/pally.mp3`. Storage 및 signed URL 반환 로직은 `service_role`만 사용, RLS 정책과 함께 `user_id` 기반 소유권 보장 필요.
- **P1 — Achievements / activity events**
  - AI 연동으로 필요한 부분: `feedback`→`activity-events` 매핑(예: 교정 아이템을 `feedback_item_opened`로 기록) 및 `GET /achievements`에서 feedback 기반 task 완료 계산에 필요한 데이터 보장.
- **P2 — Observability**
  - 현재 `_TURN_METRICS` 등 존재. 피드백 생성·signed URL 발급·idempotency hits도 metric으로 남기기.
- 문서 업데이트 요청
  - README_API.md에 다음 변경사항을 반영해 주세요:
    - Auth: README의 "MVP에서는 없음" 문구 제거. 실제는 `Authorization: Bearer {access_token}` 필요(명세).
    - Turn 오디오 제한(30초·10MiB)과 `/api/stt`의 목적(개발용 / 긴 음성 처리 구분) 명확화.
    - Feedback shape 변경 (`feedback: FeedbackItem[]`) 및 `pally.audio_url` 필드 명시.
    - Idempotency behavior 간단 표(409 responses, Retry-After header).
    - Quota reservation 개요(예약/확정/롤백 흐름).

### 수신: Frontend (FE) — AI 파트 관련 요청 (요약)

- **P0 — Authorization 헤더 포함**
  - 서버는 Supabase JWT 검증을 기대합니다. 모든 보호된 요청에 `Authorization: Bearer {access_token}`을 포함하도록 수정하세요. 현재 README에는 "MVP에서는 없음"으로 되어 있어 혼동됩니다.
- **P0 — `Idempotency-Key` 사용 규칙**
  - 모든 비용·데이터 생성 POST(예: `POST /conversations`, `POST /conversations/{id}/turns`, `POST /billing/checkout`)에 `Idempotency-Key: UUID`를 헤더로 포함.
  - 동일 작업(재시도) 시 동일 키 사용. 새 동작(다른 오디오/다른 사용자 입력)은 새 키 사용.
  - 409 응답 처리:
    - `idempotency_in_progress` → `Retry-After` 헤더를 읽고 재시도.
    - `idempotency_conflict` → 사용자에게 "작업이 변경되어 재시도할 수 없습니다" 안내.
- **P0 — Multipart upload 규칙(녹음) 및 클라이언트 제한**
  - Turn 업로드: `Content-Type: multipart/form-data`, field `audio`.
  - 클라이언트에서 미리 검증:
    - 최대 30초 녹음, 최대 10 MiB 파일 크기.
    - 허용 MIME: `audio/webm`, `audio/wav`, `audio/mp4`, `audio/mpeg`.
    - 녹음 툴(브라우저 MediaRecorder) 출력 그대로 전송 시 `audio.content_type` 확인.
  - FE는 STT 단독 엔드포인트(`/api/stt`)와 turn endpoint(`.../turns`)를 혼동하지 않도록 UI 흐름을 분명히.
- **P0 — 응답 형식 처리: partial / warnings / feedback 배열**
  - `create_turn` 응답에서:
    - `status` ∈ `completed`|`partial`|`failed`.
    - `feedback`: array (빈 배열 가능) — `[]`은 정상(수정 없음). `feedback_failed`는 `status: "partial"` 및 `warnings`로 표시.
    - `pally.audio_url`과 `audio_expires_at` 사용: 15분 유효 signed URL. 만료 후 `GET /conversations/{id}` 재요청으로 새 URL을 받도록 UI 처리.
    - `quota` 오브젝트(remaining_turns, daily_limit, exhausted, resets_at)를 받아서 quota UI 갱신.
  - 오류 처리:
    - `422 speech_not_recognized` → 사용자에게 "음성이 인식되지 않음" 안내와 녹음 재시도 옵션.
    - `429 quota_exceeded` → 잔여/리셋 시간 안내.
- **P0 — Idempotency + Retry UX**
  - 동일 키 재전송 처리: FE 재시도 로직은 같은 키로 시도(예: 네트워크 실패 복구).
  - 재시도 시 UI가 중복 결제/중복 전송처럼 보이지 않게 '처리중' 상태를 유지.
  - `turn_in_progress` 409 수신 시 사용자에게 "이 대화에 이미 요청이 진행 중입니다" 메시지 및 자동 재시도 옵션.
- **P1 — EMA 누적 axes 관리**
  - `feedback` 또는 `create_turn` 응답의 `axes` 값을 로컬 상태(Store)에 보관하고, 이후 서버-허용 시 `current_axes`로 전달하지 않도록 주의(명세에 따르면 server-side만 신뢰). 정확 권장: FE는 응답의 `axes`를 시각화에 사용하되, 다음 요청에서 `current_axes`를 직접 보내지 말고 server 제공 값을 활용하도록 API 규칙을 확인할 것(명세에서는 server가 profile·이전 turn을 로드하여 사용).
  - Note: README_API.md suggests client passes `current_axes` between calls; spec prefers server-managed axes. BE와 협의 필요: FE가 계속 `current_axes`를 보내려면 BE가 이를 허용·검증해야 함. 권장: FE stop sending server state and rely on server history.
- **P1 — Achievements / History**
  - `GET /achievements`이 서버에서 정확히 3개의 `daily_tasks`를 반환하고 `streak_count`를 제공한다는 점에 맞춰 FE 구현 필요.
  - `History` 화면의 "대화하기" 버튼은 **same conversation reopen**을 호출 (`POST /conversations/{id}/reopen`) — FE must not create a new conversation for "resume".
- **P1 — TTS playback and expiring URLs**
  - Use `pally.audio_url` (signed) and not inline base64. If backend still returns base64 for some endpoints, FE must support both but prefer signed URL once available.
  - When audio expires, FE should request `GET /conversations/{id}` again to refresh signed URL.
- **P1 — UI states for partial**
  - Distinguish `feedback: []` (정상, no feedback) vs `feedback_failed` (error) in UI. Map warnings codes to user-friendly messages.
- **P2 — Telemetry**
  - FE should send `POST /activity-events` for allowed events: `feedback_item_opened`, `achievements_opened`, etc. Ensure dedup and idempotency header on these events.

## [AI] BE 전달 사항

**수신: Backend (BE) — analyzer 어댑터 교체 요청**

- **배경**: `ai/analyzers.py`에 `get_axis_analyzer()` 어댑터가 있고, 이번에 `hybrid` 모드 + ML 실패시 자동 rule fallback을 추가했어. `backend/main.py`는 지금 이 어댑터를 안 쓰고 `analyze_utterance()`를 3곳(create_turn/`/api/chat`, `/api/feedback`, 다른 1곳)에서 직접 호출 중이야.
- **요청**: 각 호출부에서 아래 코드를 대신 아래 코드로 바꿔줘. `apply_ema()`/`compute_character()`는 그대로 `dict`를 받으니 나머지 로직은 안 건드려도 돼.

  ```py
  from ai.analyzer import analyze_utterance
  raw_axes = analyze_utterance(text)
  ```

  ```py
  from ai.analyzers import get_axis_analyzer
  raw_axes = get_axis_analyzer().analyze(text).model_dump()
  ```

- **선택 방식**: 환경변수 `PALLY_AXIS_ANALYZER=rule|ml|hybrid` (기본값 `rule`). Railway에는 지금 아무것도 안 넣으면 기존과 동일하게 rule-based로 동작하니 당장 위험 없어. `ml`/`hybrid`는 아직 실험용이라 production 기본값은 `rule` 유지 권장.
- **실패 안전성**: `ml`/`hybrid` 모드도 내부적으로 rule-based로 자동 폴백해서, 잘못 설정해도 `/api/chat`이 깨지지 않아.
- **참고(팀 공유용)**: Week 2 산출물(`ai/ml_baseline.py` 등)이 실제로는 master에 merge된 적이 없어서 `ai/analyzers.py`가 import 자체가 안 되는 상태였어(week3 브랜치 정리 때 누락된 것으로 보임). 이번에 복원해서 지금은 정상 동작해. BE가 이미 이 어댑터를 쓰고 있었다면 영향 있었을 텐데, 확인해보니 아직 안 쓰고 있어서 다행히 실사용엔 문제 없었어.

## [AI] W4 작업내용

### 1. API 명세서 검토 — BE/FE 전달사항 정리

Pally API 명세서(§4.6 turns, §5 공통 타입, §7 결정사항)를 실제 코드(`ai/`, `backend/main.py`)와 대조해서 BE/FE 전달사항 초안을 검토·수정했다.

FE 전달사항은 전부 FE 소관으로 확인, 수정 없음.

BE 전달사항 중 3건은 실제로는 AI 파트가 먼저 처리했어야 하는 항목이라 아래처럼 정정:

| 항목 | 원래 초안 | 정정 |
| --- | --- | --- |
| Turn API feedback 통합 | BE에게 `_call_gemini_feedback`(legacy, shape 다름) 재사용/신규 구현 요청 | `ai.generate_feedback.generate_feedback()`을 그대로 호출하도록 변경 — AI가 이미 구현해서 전달 |
| FeedbackItem 스키마 동기화 | BE에게 `contracts.py`(AI 파트 파일)에 모델 추가 요청 | AI가 `ai/contracts.py`에 `FeedbackItem` 모델 직접 추가, BE는 자기 쪽 응답 모델만 맞추면 됨 |
| Feedback 실패/partial 규칙 | `generate_feedback()`이 실패 신호를 안 주는 상태에서 BE에게 partial 구분 요청 | `generate_feedback()` 반환을 `(items, failed)` 튜플로 변경 — BE가 `failed=True`일 때만 `feedback_failed` warning 처리하도록 구분 가능해짐 |

### 2. BE 질문 대응 — `generate_feedback()` 함수 전달

- BE 요청: turn 처리 중 호출할 동기 함수 `generate_feedback(utterance, pally_reply, level) -> list[FeedbackItem]`
- 전달: `ai/generate_feedback.py` 구현 완료, 반환 shape `{original, corrected, explanation_ko}`, 타임아웃 10s
- **latency 정정**: 최초 답변(median 0.3–0.8s)은 실측 전 추정치였음. 실제 Gemini 2.5 Flash-Lite 호출로 8개 샘플 재측정 결과 **median ~1.6s (1.25–2.6s)** — BE에 정정 전달, TTS 호출과 `asyncio.gather` 병렬 처리 권장

#### 2.3 일일 노출 로직 (v2.0)

1. 매일 A1(오늘 대화 시작하기)을 **고정 기본 Task**로 포함한다 — Streak 조건이 "3개 모두 완료"로 강화된 만큼, 진입 장벽이 가장 낮은 task를 고정해 완주 가능성을 보장한다.
2. 나머지 29개 중 seed = hash(user_id + YYYY-MM-DD KST)로 2개를 결정적으로 선택한다. 같은 사용자·같은 KST 날짜에는 항목과 순서가 바뀌지 않는다 (API 명세서 4.12).
3. Pro 사용자에게는 E6을 선택 풀에서 제외한다.
4. 선택 결과는 daily_task_snapshots(user_id, date_kst별)에 고정 저장하고, 완료 여부는 요청 시점에 서버가 재계산해 반환한다. 클라이언트는 status를 직접 쓸 수 없다.

### 4주차 백엔드 완료 (다중 대화 / History / Feedback)

#### 완료 항목

| 엔드포인트 | 용도 | 상태 |
| --- | --- | --- |
| `GET /api/conversations` | History 목록 (pagination) | ✅ 배포·검증 |
| `GET /api/conversations/{id}` | 상세 (turns + feedback) | ✅ 배포·검증 |
| `POST /api/conversations/{id}/complete` | 대화 종료 (멱등) | ✅ 배포·검증 |
| `POST /api/conversations/{id}/reopen` | 완료 대화 재개 | ✅ 배포·검증 |

#### 핵심 동작

- **History 목록**: 최근순, cursor pagination(`limit` 기본 20·최대 50), `status` 필터(active/completed), 본인 것만
- **상세**: user+pally 메시지를 turn으로 페어링(`sequence` 1,2,3…), 각 turn에 `feedback`
- **complete**: 대화 종료. 재호출해도 같은 결과. 완료된 대화에 turn 시도 → `409`
- **reopen**: `completed → active`, **기존 turn/feedback 보존** 후 새 turn append, `reopen_count++`, 이미 active면 `409`
- **소유권**: 타인 대화는 전부 `404`

#### Feedback (중요)

- 저장·조회 **경로는 완성** — 응답에 `feedback` 필드 정상 옴
- **생성은 AI 담당 → 붙기 전까진 항상 빈 배열 `[]`**
- DB: `messages.feedback` 컬럼에 저장 예정 (AI 함수 오면 turn 처리에 연결)

#### DB 마이그레이션 (적용 완료)

- `messages.feedback` (jsonb)
- `sessions.reopened_at`, `sessions.reopen_count`

#### 검증

- 로컬 24/24 + **Railway 배포본 24/24** (실제 Supabase)

#### 아직 안 됨 (후속)

- feedback **내용 생성** (AI 팀원)
- quota (5주차), audio_url signed URL (오디오는 base64)
