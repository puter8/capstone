## [AI] W1 작업 내용

### 작업 정리

**1주차 작업 정리**

1주차에는 ML 모델을 바로 만들기보다, 기존 룰베이스 분석기를 유지하면서 나중에 ML 분석기로 교체할 수 있는 기반을 만들었다. 현재 MVP가 이미 룰베이스 5축 분석으로 동작하고 있기 때문에, 이를 삭제하지 않고 baseline/fallback으로 남겨두는 방향으로 진행했다.

진행한 작업은 다음과 같다.

- `ai/contracts.py` 추가
  - AI 파트에서 공통으로 사용할 데이터 구조를 정의했다.
  - `AxisResult`, `RedditSourceItem`, `MemeTermCandidate`, `MemeTerm`을 만들었다.
- `ai/analyzers.py` 추가
  - 기존 `analyze_utterance()`를 `RuleBasedAxisAnalyzer`로 감쌌다.
  - 이후 ML 모델은 같은 `AxisAnalyzer` 인터페이스 뒤에 붙일 수 있도록 했다.
- `ai/reddit_vocabulary.py` 추가
  - Reddit source text에서 `lowkey`, `no cap`, `main character energy` 같은 slang/meme 후보를 추출하는 skeleton을 만들었다.
  - 후보는 `safe`, `review`, `blocked`로 분류하고, `safe` term만 Pally prompt에 들어가도록 했다.
- `data/fixtures/` 추가
  - 실제 Reddit API를 아직 사용할 수 없기 때문에, 백엔드가 나중에 넘겨줄 Reddit source 형태를 가짜 데이터로 만들었다.
- `tests/test_ai_week1_contracts.py` 추가
  - 기존 룰베이스 결과와 새 wrapper 결과가 같은지, Reddit fixture가 `MemeTermCandidate`로 변환되는지 검증했다.

검증은 아래 명령으로 진행했고 모두 통과했다.

```txt
python tests/test_ai_week1_contracts.py
python tests/test_matrix.py
python -m compileall ai tests
```

**왜 이렇게 진행했는가**

현재 ML 모델은 아직 학습·평가 전이고, MVP의 `/api/chat` 흐름은 기존 룰베이스 분석 결과에 의존하고 있다. 그래서 룰베이스를 바로 삭제하면 기존 기능이 깨질 수 있고, ML이 좋아졌는지 비교할 기준도 사라진다.

따라서 1주차에는 ML 자체보다 **ML로 안전하게 전환할 수 있는 구조**를 먼저 만들었다. 이 구조 덕분에 프론트와 백엔드는 계속 같은 `axes`, `character`, `feedback`, `tts_audio` 형태를 받으면 되고, AI 내부에서는 룰베이스와 ML을 비교하거나 교체할 수 있다.

STT/TTS 배포 테스트는 Railway trial 만료로 백엔드가 내려가 있어 보류했고, Reddit 실제 API 호출도 백엔드의 접근 승인/collector 영역이라 이번 주에는 fixture 기반으로만 진행했다.

### 전달 사항

**프론트엔드 전달 사항**

1주차 AI 작업은 프론트 화면 구조에 영향을 주지 않습니다.

프론트는 내부 분석기가 룰베이스인지 ML인지 몰라도 되고, 기존처럼 API 응답의 정해진 필드만 사용하면 됩니다.

프론트와 맞춰야 하는 출력 contract는 다음입니다.

```ts
type FeedbackItem = {
  original: string;
  corrected: string;
  explanationKo: string;
};

type ChatResponseForFrontend = {
  status: "ok";
  transcript: string;
  reply: string;
  tts_audio: string;
  axes: {
    Formality: number;
    Energy: number;
    Intimacy: number;
    Humor: number;
    Curiosity: number;
  };
  character: {
    tone_casual: number;
    energy_level: number;
    humor_level: number;
  };
  feedback: FeedbackItem[];
};
```

주의할 점:

- `hint_ko` 기준이 아니라, Figma 피드백 화면 기준의 `feedback` 구조로 맞춥니다.
- `feedback`은 대화 중 힌트가 아니라 Feedback 화면에서 보여줄 데이터입니다.
- `axes`, `character` 값은 기존처럼 0~100 범위를 유지합니다.
- AI 내부가 ML로 바뀌어도 프론트에서는 별도 수정이 없도록 할 예정입니다.

**백엔드 전달 사항**

AI 쪽에서는 기존 룰베이스 분석기를 `RuleBasedAxisAnalyzer`로 감싸고, 나중에 ML 분석기를 같은 interface 뒤에 붙일 수 있게 만들었습니다.

즉 백엔드는 앞으로 AI analyzer를 호출할 때 내부 구현이 룰베이스인지 ML인지 몰라도 됩니다.

백엔드와 맞춰야 하는 부분은 다음입니다.

- `/api/chat` 응답 shape 유지
- DB 저장 구조는 `axes`, `character`, `feedback` 기준
- 기존 `hint_ko` 중심이 아니라 `FeedbackItem` 구조로 정리 필요
- Reddit 수집은 백엔드 담당
- AI는 백엔드가 넘겨주는 `RedditSourceItem[]`을 받아 `MemeTermCandidate[]`를 반환

Reddit 관련 최소 contract는 다음입니다.

```ts
type RedditSourceItem = {
  sourceId: string;
  sourceUrl: string;
  subreddit: string;
  title?: string;
  text: string;
  observedAt: string;
};

type MemeTermCandidate = {
  term: string;
  normalizedTerm: string;
  meaningKo: string;
  usageContext: string;
  subreddit: string;
  sourceId: string;
  sourceUrl: string;
  observedAt: string;
  confidence: number;
  safety: "safe" | "review" | "blocked";
};
```

주의할 점:

- Reddit 실제 API 접근, credential, collector, 저장은 백엔드 영역입니다.
- AI는 현재 fake fixture로 extractor contract만 검증했습니다.
- `review` 또는 `blocked` 후보는 Pally prompt에 넣으면 안 됩니다.
- Railway trial 만료로 STT/TTS 배포 endpoint 검증은 아직 못 했습니다.
- 백엔드가 다시 살아나면 `/api/health` → `/api/stt` → `/api/chat` → `/api/tts` 순서로 확인하면 됩니다.

요약하면:

```txt
프론트: 응답 contract만 유지하면 됨. hint_ko 말고 feedback 화면용 FeedbackItem 기준.
백엔드: AI analyzer는 교체 가능 구조로 바뀜. Reddit source 수집은 백엔드, 후보 추출은 AI.
```

#### 1.3 일일 노출 로직 (MVP 최소 구현)

1. 32개 중 seed = hash(user_id + YYYY-MM-DD KST)로 3개를 결정적 랜덤 선택한다.

#### 2.2 결제 Provider 확정 근거

- 정보구조도 v5의 라우팅 다이어그램(§2)에 "V2-18 요금제 → 결제 → 결제 성공?"이 이미 존재하고, 화면 상세(§3)에는 "스토어/PG 결제 호출"이라고 명시되어 있다. 즉 디자인은 **모바일 네이티브 구독**을 전제로 만들어졌다 — 웹 PG를 새로 붙이는 대신 스토어 결제를 그대로 따르는 것이 디자인·개발 리소스 양쪽에서 가장 적은 추가 작업이다.
- iOS/Android 모두 디지털 구독 상품은 각 스토어 정책상 인앱결제(StoreKit / Play Billing)를 **의무적으로 사용**해야 한다. 자체 PG로 우회할 수 없다.
- RevenueCat은 두 스토어의 영수증 검증·구독 갱신·해지·복원(Restore Purchases)을 하나의 SDK로 처리하며, Supabase에 웹훅으로 구독 상태를 동기화할 수 있어 백엔드 커스텀 구현 부담을 줄인다.

#### 2.3 MVP 결제 범위 (포함 / 제외)

| 구분 | 포함 (MVP) |
| --- | --- |
| 노출 트리거 | 대화량 소진(V2-09) → "show the plans" → V2-18 진입 |
| 플랜 선택 | Monthly / Yearly 2개 플랜 |

#### 0. 공통 규칙

- ID 형식: `{prefix}_{random}` — `user_`, `conv_`, `turn_`, `fb_`
- 시간: ISO 8601 UTC 문자열 (`2026-07-26T09:00:00Z`)
- 인증: 모든 요청은 Supabase Auth 세션 쿠키/JWT 기준, `userId`는 서버가 세션에서 추출 (요청 바디에 넣지 않음)
- 실패를 빈 문자열/빈 배열로 표현하지 않는다 (계획서 8.2 원칙) → 실패는 반드시 `status`나 `error` 필드로 명시
